## Bug #1: MapView con Coordenadas Inválidas (NaN)

### Error:
```
ERROR Invariant Violation: [1265,"AIRMap",21,{"flex":1,"region":null,"initialRegion":{"latitude":"<<NaN>>","longitude":"<<NaN>>"...
```

### Causa:
Las coordenadas `originLat`, `originLng`, `destinationLat`, `destinationLng` estaban llegando como **strings** desde el backend en lugar de números, causando que el MapView recibiera `NaN` al intentar operaciones matemáticas.

### Solución:
**Archivo:** `Frontend/src/screens/Driver/AvailableRidesScreen.tsx`

```typescript
// ANTES (causaba NaN):
{item.originLat && item.originLng && item.destinationLat && item.destinationLng && (
  <MapView
    initialRegion={{
      latitude: (item.originLat + item.destinationLat) / 2,  // NaN si son strings
      longitude: (item.originLng + item.destinationLng) / 2,
      ...
    }}
  />
)}

// DESPUÉS (convierte y valida):
const renderRideItem = ({ item }: { item: AvailableRide }) => {
  // Convertir coordenadas a números
  const originLat = Number(item.originLat);
  const originLng = Number(item.originLng);
  const destinationLat = Number(item.destinationLat);
  const destinationLng = Number(item.destinationLng);
  
  // Validar que sean números válidos
  const hasValidCoordinates = 
    !isNaN(originLat) && !isNaN(originLng) && 
    !isNaN(destinationLat) && !isNaN(destinationLng) &&
    originLat !== 0 && originLng !== 0 &&
    destinationLat !== 0 && destinationLng !== 0;
  
  return (
    // ...
    {hasValidCoordinates && (
      <MapView
        initialRegion={{
          latitude: (originLat + destinationLat) / 2,  // Ahora son números
          longitude: (originLng + destinationLng) / 2,
          ...
        }}
      />
    )}
  );
};
```

### Resultado:
✅ MapView solo se renderiza si las coordenadas son válidas  
✅ No más errores de NaN  
✅ Mejor manejo de casos edge

## Bug #2: Expo Notifications - projectId Inválido

### Error:
```
ERROR ❌ Error inicializando notificaciones: [Error: Error encountered while fetching Expo token, expected an OK response, received: 400 (body: "{"errors":[{"code":"VALIDATION_ERROR","type":"USER","message":"\"projectId\": Invalid uuid."...
```

### Causa:
El `projectId` en `app.json` tenía un formato inválido: `e8f4c3b2-9d1a-4e7f-8c5b-2a3d4e5f6g7h` (nota la **'g'** al final, los UUIDs solo usan 0-9 y a-f).

### Solución:
**Archivo:** `Frontend/app.json`

```json
// ANTES (UUID inválido):
"projectId": "e8f4c3b2-9d1a-4e7f-8c5b-2a3d4e5f6g7h",
                                              ↑ 'g' es inválido

// DESPUÉS (UUID válido):
"projectId": "e8f4c3b2-9d1a-4e7f-8c5b-2a3d4e5f6a7b",
                                              ↑ 'a' es válido
```

### Resultado:
✅ projectId ahora es un UUID válido  
✅ Notificaciones de Expo funcionarán correctamente  
✅ No más errores 400 de validación

## Notas Técnicas

### Sobre las Coordenadas:
El backend (Firebase Functions) está retornando las coordenadas como strings desde PostgreSQL. Esto es normal porque PostgreSQL almacena DECIMAL como strings en JSON. La solución correcta es convertirlas en el frontend.

**Alternativa (Backend):**
Si quieres que el backend las envíe como números, puedes modificar `rides.ts`:

```typescript
// En getAvailableRides
return {
  id: ride.id,
  originLat: parseFloat(ride.origin_lat),  // Convertir a número
  originLng: parseFloat(ride.origin_lng),
  destinationLat: parseFloat(ride.destination_lat),
  destinationLng: parseFloat(ride.destination_lng),
  // ...
};
```

Pero la solución actual (frontend) es más robusta porque valida los datos.

### Sobre el projectId:
El projectId de Expo debe ser un UUID válido (formato: 8-4-4-4-12 caracteres hexadecimales). Si necesitas crear un proyecto nuevo en Expo, usa:
```bash
npx expo login
npx expo whoami
```
